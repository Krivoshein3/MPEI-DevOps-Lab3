# Лабораторная работа № 3 — Московская афиша

## Задание

**Вариант 33:** разработать интерфейс для поиска альтернатив выбранному событию — мероприятий того же жанра с сортировкой по близости цены к исходному.

[Индивидуальное задание](https://github.com/Krivoshein3/MPEI-DevOps-Lab3/issues/1).
Используется готовый [бэкенд moscow-events](https://github.com/nelkor/moscow-events). В этом репозитории находятся фронтенд и конфигурация запуска.

## Быстрый запуск

Нужны Git, работающий Docker Engine и Docker Compose v2. На Windows можно использовать Docker Desktop в режиме Linux containers. При первом запуске нужен интернет для загрузки образов.

```sh
git clone https://github.com/Krivoshein3/MPEI-DevOps-Lab3.git
cd MPEI-DevOps-Lab3
docker compose up -d
```

Откройте **http://localhost:8080**. Первый запуск может занять несколько минут: Docker скачивает образы, затем бэкенд создаёт таблицы и заполняет пустую базу демонстрационными данными.

Проверить состояние:

```sh
docker compose ps
docker compose logs --tail=100 backend
```

База данных и бэкенд должны перейти в состояние `healthy`, фронтенд — `Up`. Готовность API также проверяется по адресу http://localhost:8080/health/ready. Swagger доступен по адресу http://localhost:8080/docs.

## Как пользоваться

1. Найдите исходное событие по названию или описанию. Нажмите «Найти»; при необходимости выберите жанр.
2. Нажмите на карточку события в каталоге.
3. Справа появятся другие опубликованные мероприятия того же жанра. Для каждого указаны цена и разница относительно исходного события.
4. Нажмите «Сравнить с этим», чтобы сделать альтернативу новым исходным событием.
5. Кнопки «Показать ещё» загружают следующую страницу каталога или раскрывают следующие найденные альтернативы. «Обновить» повторно загружает каталог и подборку.

Альтернативы сортируются по возрастанию `abs(цена альтернативы − цена исходного события)`. Например, для цены 1000 ₽ события за 1100 ₽, 800 ₽ и 1500 ₽ будут показаны именно в таком порядке. При одинаковой разнице сначала идёт событие с более ранней датой, затем используется UUID для стабильного порядка. Исходное событие исключается из результатов.

При поиске альтернатив фронтенд получает **все страницы** событий выбранного жанра и только затем сортирует их. Поисковая строка каталога не ограничивает альтернативы. Бесплатные события учитываются с ценой 0 ₽. События без свободных билетов остаются в подборке с соответствующей подписью. Фильтра «только будущие» нет; даты отображаются в часовом поясе Москвы. При пустом каталоге или отсутствии альтернатив показывается пояснение, при ошибке API — сообщение с возможностью повторить запрос.

## Как устроен запуск

```text
Браузер → localhost:8080 → frontend (NGINX, порт 80)
                              │ /api/v1/...
                              ▼
                         backend:8000
                              │
                              ▼
                            db:5432
                              │
                              ▼
                     volume postgres_data
```

| Сервис | Назначение |
| --- | --- |
| `frontend` | Собирается из `frontend/Dockerfile`. NGINX отдаёт HTML, CSS и JavaScript, а запросы `/api/`, документацию и проверки здоровья передаёт бэкенду. |
| `backend` | Готовый образ `ghcr.io/nelkor/moscow-events:1.0.0`. Предоставляет API, создаёт схему и заполняет пустую базу. |
| `db` | Образ `postgis/postgis:17-3.6`: PostgreSQL 17 с расширением PostGIS для географических данных бэкенда. |

Compose автоматически создаёт общую сеть. В ней имена сервисов работают как DNS-имена: `backend` подключается к `db`, а NGINX — к `backend`. `localhost` внутри контейнера означал бы сам этот контейнер.

Основные параметры `compose.yml`:

- `build.context: ./frontend` — папка, из которой собирается образ фронтенда.
- `ports: 127.0.0.1:8080:80` — порт 8080 компьютера направляется на порт 80 фронтенда. Приложение доступно только с этого компьютера; порты БД и бэкенда наружу не публикуются.
- `environment` — настройки базы и подключения к ней. `PG_*` читает бэкенд, `POSTGRES_*` — контейнер БД. Название БД, пользователь и пароль должны совпадать.
- `healthcheck` — проверка готовности PostgreSQL через `pg_isready`. У бэкенда проверка `/health/ready` уже встроена в образ.
- `depends_on` с `service_healthy` — бэкенд стартует после готовности БД, фронтенд — после готовности бэкенда. Это порядок первоначального запуска, а не постоянный контроль зависимостей.
- `volumes` — данные PostgreSQL находятся в именованном томе `postgres_data` и сохраняются при пересоздании контейнеров.
- `restart: unless-stopped` — Docker перезапускает завершившийся контейнер, если он не был остановлен вручную. Статус `unhealthy` сам по себе не вызывает перезапуск.
- `SEED_MODE: sample` — заполнение пустой БД демонстрационным набором; существующие данные сохраняются.

В `frontend/nginx.conf` у `proxy_pass http://backend:8000` нет завершающего `/`, поэтому исходный путь `/api/v1/...` сохраняется. Фронтенд использует относительные URL и работает с API через тот же адрес, что и страница.

## Пароль локальной базы

Запуск не требует `.env`: в Compose задан учебный пароль по умолчанию. Для своего значения **до первого запуска** создайте `.env` в корне репозитория:

```dotenv
DB_PASSWORD=your_local_password
```

Файл `.env` исключён из Git. Выражение `${DB_PASSWORD:-lab3_local_password}` подставляет значение переменной или учебное значение, если переменная не задана либо пуста. Для публичного сервера эта конфигурация не предназначена.

Изменение `.env` не меняет пароль пользователя в уже инициализированной БД. Для существующего тома пароль нужно менять средствами PostgreSQL; не удаляйте том с нужными данными ради смены настройки.

## Управление приложением

Выполняйте команды из корня репозитория.

```sh
# Остановить и удалить контейнеры и сеть, сохранив данные БД
docker compose down

# Запустить снова
docker compose up -d

# Пересобрать фронтенд после изменения его файлов
docker compose up -d --build

# Смотреть журналы всех сервисов (Ctrl+C прекращает просмотр)
docker compose logs -f

# Проверить итоговую конфигурацию Compose
docker compose config --quiet
```

**Удаление учебных данных:** `docker compose down -v` удаляет и контейнеры, и том БД. Выполняйте эту команду только если данные больше не нужны. Следующий запуск создаст новый демонстрационный набор.

## Если что-то не работает

- **Docker недоступен:** запустите Docker Desktop / Docker Engine и проверьте `docker info`.
- **Порт 8080 занят:** измените только порт компьютера, например на `127.0.0.1:8081:80`, выполните `docker compose up -d` и откройте http://localhost:8081.
- **Бэкенд не становится healthy:** проверьте `docker compose logs --tail=100 db backend`. Убедитесь, что пароль соответствует существующей БД.
- **Ошибка скачивания образа:** проверьте доступ к Docker Hub и `ghcr.io`, затем повторите запуск.
- **Ошибка API в интерфейсе:** проверьте `docker compose ps` и `/health/ready`, затем нажмите «Обновить» или «Повторить загрузку».
- **Событий нет:** сбросьте поиск и жанр. В пользовательском наборе может не быть опубликованных событий; повторный запуск не перезаполняет существующую БД.

## Файлы проекта и проверки

```text
compose.yml              # Три сервиса, зависимости и том данных
frontend/
  Dockerfile             # Образ NGINX со статическими файлами
  nginx.conf             # Раздача фронтенда и проксирование API
  index.html             # Разметка интерфейса
  styles.css             # Адаптивное оформление
  app.js                 # Запросы API и взаимодействие с интерфейсом
  logic.mjs              # Сортировка альтернатив и обход страниц
  logic.test.mjs         # Тесты логики
```

Фронтенд написан на обычном JavaScript без сторонних зависимостей. Node.js не нужен для запуска приложения в Docker, но нужен для тестов (рекомендуется версия 22 или новее):

```sh
node --test frontend/logic.test.mjs
node --check frontend/app.js
```

Тесты проверяют исключение исходного события и чужих жанров, фильтрацию статусов, сортировку по абсолютной разнице цены, бесплатные события, равенство цен, обход страниц и ошибки загрузки. Они не заменяют проверку полного запуска через Docker.

Для ручной проверки запустите приложение, выберите событие и убедитесь, что жанр всех альтернатив совпадает, исходного события нет среди результатов, а абсолютная разница цен не убывает. После `docker compose down` и повторного запуска данные должны сохраниться.
